# `larena/storage`

> **Для кого:** разработчик данных. **Результат:** работать с версионированной
> записью через package runtime. **Источник:** код пакета (`src/`, `access.yaml`,
> `api.yaml`, `eb07a962`), CHANGELOG, package README и Specs: движок хранилищ
> для миллионов записей, витрины сайта, шифрование полей, перенос хранилища.
> **Статус:** developer-testable persistent foundation; проверено по коду
> 26.10.2026.

Storage владеет структурами хранения, версиями схем и записей, а также
контролируемыми мутациями. Текущий интеграционный вход —
`Larena\Storage\Runtime\DatabaseStorageWorkbench`.

- Composer: `larena/storage`.
- Владелец: record/schema versions and mutations.
- Зрелость: developer-testable persistent foundation.

Пакет зависит от `larena/core`, `larena/property`, `larena/access`,
`larena/queue` (фоновые задачи) и `larena/secret` (ключи шифрования). Тип поля
сначала нормализует Property, решение операции принимает Access, затем Storage
создаёт или меняет запись с проверкой версии.

Какие типы поля можно искать, сортировать, индексировать и шифровать, Storage
не решает сам: он читает это из объявления типов Property. Хранилища принимают
и общие типы Property: «Цвет» (`color`), «Телефон» (`phone`), «Адрес страницы»
(`url`), «Ссылка» (`link`) и «Выбор из справочника» (`lookup`). Цвет, телефон и
адрес фильтруются по точному значению; телефон в фильтре приводится к той же
форме, что и при записи, поэтому находится в любом написании. Ссылка хранится
как адрес с подписью и не фильтруется. Значение из справочника проверяется по
его источнику, хранится в индексированной колонке, фильтруется и сортируется.

Сами хранилища тоже служат справочником для Property — источник
`storage.structures` (`StorageStructureOptionSource`): он перечисляет активные
хранилища области так, как их видит человек.

## Жизненный цикл данных

- Структуру можно архивировать и восстановить. Архивная структура сохраняет
  записи и историю, показывается в списке только по запросу и не принимает
  изменений.
- Окончательное удаление явное и касается только архивных данных:
  `purgeRecords()` удаляет архивные записи, `purgeStructure()` — архивную
  структуру со всеми записями. Удаляются все версии, локализованные значения,
  публикации и связи. Операция отклоняется, пока на удаляемые записи ссылается
  запись снаружи, в том числе через поле «Запись хранилища» (`record@1`).
  Идентификатор удалённой структуры повторно не используется.
- Поле «Запись хранилища» проверяется при записи: оно должно указывать на
  активную запись своего хранилища в той же области.
- Сколько версий каждой записи хранить, задаёт структура (`history_keep`); пусто
  — все. Текущая и опубликованные версии не удаляются.
- Признак поля `hidden` влияет только на отображение; поле и значения остаются.
- `filterOperators()` сообщает, какие операторы фильтра доступны для каждого
  типа поля Property.

## Изменение полей

Добавить или удалить поле можно без перезаписи записей: каждая версия помнит
схему, под которой её записали, а при чтении приводится к текущей. Добавленное
необязательное поле читается пустым. Значение удалённого поля больше не
читается, и возврат старой версии его не вернёт.

Изменение, которое затрагивает данные, — смена типа, обязательность, другие
ограничения поля, шифрование — проверяет каждую запись:

1. До подтверждения `checkFieldChange()` считает, сколько текущих записей не
   подойдут под новые настройки (до 10 000 записей, с примерами ID). Это только
   чтение, без блокировок.
2. `migrateStructure()` выполняет изменение. До 5000 записей — сразу; если хоть
   одна запись не подходит, ничего не меняется. Больше — фоновой задачей
   `storage.schema.migrate` по частям; пока она идёт, списки работают по старым
   колонкам, а в конце структура переключается одной транзакцией.
3. `cancelFieldChange()` отменяет идущее изменение; поле и записи остаются
   прежними.

Настройки, которые влияют только на форму, фильтр или список (`mask`,
`placeholder`, `step`, `unit`), меняются сразу и записи не проверяют.

## Витрины и списки

У каждого хранилища есть витрина — отдельная таблица с типизированными
колонками, которая пишется в той же транзакции, что и запись. Списки, фильтры,
сортировка, поиск и подсчёт идут по ней в SQL (`StorageViewQueryCompiler`), а
продолжение страницы — по ключу последней строки (keyset), поэтому глубокие
страницы не замедляются.

- **Порядок по умолчанию.** Системный ключ сортировки `_created_at` с индексом
  `(state, created_at, record_id)`; «сначала новые» —
  `[{field: _created_at, direction: desc}]`.
- **Подсчёт.** В режиме `Auto` число считается точно до 10 000 совпадений за
  250 мс, иначе возвращается оценка с `countExact = false` (в админке — «~N»).
  `Exact` считает всегда точно, `Skip` не считает.
- **Поиск.** Ищет по началу слов в полях с признаком `searchable`; на MySQL
  через отдельную таблицу с FULLTEXT-индексом. Запрос — не длиннее 100
  символов.
- **Индексы.** Числа, даты, флажки, выборы, пользователи, записи и справочники
  индексируются автоматически; строку до 255 символов можно индексировать по
  запросу (`indexed`). В одной витрине — не больше 40 индексов полей.
- **Медленная сортировка.** Если большой список сортируется по полю без
  индекса, Storage сообщает об этом, и админка показывает подсказку.
- **Готовность.** Хранилище до 5000 записей строит витрину прямо в запросе.
  Для большего список отвечает `storage_view_not_ready`, а перестройка
  ставится в очередь (`storage.view.rebuild`, по частям, с продолжением).

Обслуживание: `larena:storage:view:rebuild` строит витрины, а
`larena:storage:view:check --repair` сверяет их с версиями записей и чинит.
Root запускает перестройку недостающих витрин каждые десять минут и сверку раз
в сутки. Замер движка — `larena:storage:bench` на отдельной базе.

## Публикация

Отложенную публикацию выполняет команда `php artisan storage:publication:sweep`.
Storage ставит её в планировщик Laravel раз в минуту, поэтому на хостинге нужна
одна строка cron: `* * * * * cd /путь/к/larena && php artisan schedule:run`.
Чтение страницы никогда не публикует запланированную запись.
Каждая такая публикация записывается в историю от имени `system:scheduler`.

Если у опубликованной записи запланирована новая версия, на сайте до срока
остаётся прежняя; в срок планировщик выпускает новую. Снятие с публикации
оставляет историю, сообщает, какая версия была снята, и не возвращает в
публикацию более старую версию.

Каждый переход публикации — публикация, снятие, планирование, архив и
публикация по расписанию — пишется в журнал аудита: кто, какая запись, область,
язык, версии и номер корреляции, без значений полей. Это касается любого пути:
операции, планировщика и прямого вызова. Если событие аудита не записалось,
переход отменяется. На MySQL проверено, что после переподключения читаются те же
опубликованные версии и та же история (`composer test:mysql-publication`).

Опубликованные страницы сайта попадают в поиск (`/search`) как источник
`storage.site_pages`: один документ на запись и язык, со ссылкой
`/site/<язык>/<ключ>` и только с публичными полями, записанными для этого языка.
Документ появляется в поиске сразу при публикации и исчезает при снятии.
Порядок изменений гарантирует `projection_version` — номер, который только растёт
при каждой публикации, снятии и переводе. Схема согласована с пакетом Search.

### Витрины сайта

Для опубликованных записей у хранилища есть своя витрина сайта — по одной части
на область и язык, только с публичными полями опубликованной версии. Она
обновляется в транзакции публикации и перевода. Если что-то записано мимо неё,
витрина замолкает, и чтение идёт прежним точным путём: короткого или неверного
списка она не отдаёт.

Публичный список с фильтрами, поиском, сортировкой и подсчётом —
`publishedList()` (операция `storage.read.published_list`, REST
`GET /api/v1/site/list`, обработчик даёт Root). `publishedTimes()` сообщает,
когда записи опубликованы, — для `lastmod` в карте сайта.

## Переводы и видимость

Перевод проверяется так же, как общее значение: поле должно быть в схеме той
ревизии, к которой пишется перевод, а значение проходит проверку типа Property.
Неверный перевод не сохраняется.

Публичное чтение берёт порядок языков у Lang: запрошенный язык, запасные языки
сайта (`LARENA_SITE_FALLBACK_LOCALES`), затем язык приложения по умолчанию.
Страница без перевода показывает ближайший найденный перевод, а общее значение —
только после него.

Какие поля переводятся, какие из них обязательны и можно ли оставлять перевод
неполным, говорит сама схема хранилища (`localized`, `partial_locales`), а не
тот, кто пишет перевод. Значение для основного языка приложения (`app.locale`)
только уточняет общее и может быть неполным. Каждый перевод пишется в журнал
аудита — с ключами полей, без значений. В опубликованном чтении у каждого
значения есть отметка источника: `exact` — перевод на запрошенном языке,
`fallback:<язык>` — запасной язык по порядку Lang, `shared` — общее значение.

Кто какую опубликованную запись может прочитать, решает порт
`PublishedReadVisibility`. Операции чтения, REST-чтение сайта и HTML-страница
сайта берут фильтр у него, поэтому скрытая запись везде отвечает тем же «не
найдено», что и несуществующая. По умолчанию все опубликованные записи
публичны: построчных прав в Access пока нет.

Ключ, по которому сайт находит страницу (обычно `slug`), объявляет тот, кто по
нему маршрутизирует, — для сайта это Root. Storage не даст опубликовать вторую
страницу с уже занятым ключом в той же области и на том же языке
(`key_conflict`), а планировщик оставит такую публикацию запланированной и
сообщит причину. Опубликованные ключи хранятся в отдельной таблице;
`larena:storage:published-keys:rebuild` строит её заново, Root запускает это
каждые десять минут.

Индекс поиска — копия: `search:reindex storage.site_pages` восстанавливает его из
Storage, даже если документы испорчены, потеряны или лишние. Сайт можно отдавать
и без админки — headless-сборка `compositions/headless_v1` работает только через
REST, без Layout, UI и Admin; проверено на SQLite и MySQL.

## Шифрование полей

Поле может быть зашифровано (`encrypted: true`): строка, текст, целое число,
число, дата и дата со временем. Такое поле видно только в админке и никогда не
бывает ключом записи, полем поиска или индекса.

- Значение шифруется XChaCha20-Poly1305 ключом данных хранилища, а этот ключ —
  главным ключом сайта, который по умолчанию выводится из `APP_KEY`
  (`larena/secret`).
- Зашифрованное значение не попадает в витрины, поиск, журнал аудита и перенос
  хранилища. Открыть его может только тот, у кого есть право
  `storage.workbench.record.decrypt`; каждый просмотр пишется в аудит.
- Включение и выключение шифрования у поля со значениями и смена ключа идут
  фоновой задачей по частям, с продолжением после сбоя. Новые записи сразу
  следуют новой настройке.
- Команды: `larena:storage:encryption:status`, `…:rotate` и `…:rewrap` (после
  смены главного ключа сайта).

Старые резервные копии базы и журналы MySQL всё ещё содержат открытые значения
— шифрование их не трогает.

## Перенос хранилища (SitePack)

Хранилище можно выгрузить архивом и загрузить на другой сайт.

- **Выгрузка** (`storage.sitepack.export`): структура, все записи с переводами и
  публикацией и их файлы, без истории изменений. Идёт фоновой задачей с
  продолжением; архив видит только тот, кто его сделал. Зашифрованные значения
  в архив не попадают, если не попросить их открытым текстом.
- **Загрузка** (`storage.sitepack.import`): архив принимается и проверяется
  целиком, затем строится план — что будет создано, какие файлы и ссылки
  найдены, какие предупреждения. План закрепляется отпечатком `sha256:`, и
  загрузка выполняется только по нему; если на сайте что-то изменилось, план
  нужно проверить снова. Записи по умолчанию приходят черновиками; сохранить
  публикацию может тот, у кого есть право публиковать. Повторно тот же архив
  загружается только копией с новыми ID.
- Команды: `larena:storage:sitepack:export`, `…:import`, `…:sweep`. Root
  удаляет архивы старше недели раз в сутки.

Общий стандарт переноса хранилищ с Bitrix (`simai.storage`) пока только
черновик на согласовании; адаптера нет.

## Проверка

Root quality gate проверяет базовые мутации, CRUD и повторное чтение. Отдельный
hierarchy test ранее блокировался package test autoload в общей vendor-сборке;
не используйте его отсутствие как доказательство корректности иерархии.
Витрины на MySQL проверяет отдельный набор `composer test:mysql-view`.

## Связи и роли структур

Связь между записями проверяется до записи: запись-источник принадлежит
структуре, цель существует и относится к объявленной структуре или роли,
родитель в дереве — из той же структуры и той же области. Схема может объявить
свои связи вместе с политикой удаления (`restrict`, `cascade`, `detach`); тогда
связь создаётся только так, как объявлено. Политика удаления действует везде:
в операции `storage.relation.delete_record` и при удалении записей навсегда.
Дерево показывает пользователю записи его области, остальные только считает.
Создание, перемещение и удаление связей пишутся в аудит, перемещение — одним
событием со всем перемещённым поддеревом.

У каждой стартовой роли есть образец структуры, которая ей соответствует.
Отказ в привязке приходит с разбором: каких полей, связей и жизненного цикла
не хватает. Новая версия роли не меняет старую: план показывает, что
изменилось и какие привязки ещё на старой версии, а перенос привязки проверяет
структуру на новую версию. Пакет-потребитель объявляет, от каких ролей зависит
(сайт Root — от `site_node@v1`), и получает структуры только по объявленным
ролям. При загрузке архива переноса роль привязывается вместе с нужными ей
связями и жизненным циклом.

## Готовность фич

Пять фич Storage — роли структур, связи, значения по локалям, публикация и
чтение опубликованного — реализованы, но не подтверждены целиком: на
2026-10-22 выполнено 33 из 34 критериев приёмки. С выходом переноса хранилища
закрылись перенос связей и переводов между сайтами. Частично остаётся один
критерий ролей структур: перенос работает, но для стартовых ролей нет готовых
примеров архива. Матрица с тестами и списком пробелов —
`larena-specs/docs/architecture/storage-feature-acceptance-audit.md`.

## Ограничение

Прямой доступ к таблицам обходит версии, права и audit-контракт. Витрины —
производные таблицы для чтения, а не источник данных: их можно перестроить из
версий записей. Публичный универсальный генератор моделей не принят в рамках
двенадцати пакетов.

## Содержимое композиции

В профиле Minimal CMS Storage владеет структурированным содержимым и его
ревизиями. Layout хранит только типизированный `ContentBinding` с ожидаемой
ревизией. HTML не является форматом сохранения редакторского содержимого;
блочная модель может использовать JSON-подход EditorJS и проектироваться в
зарегистрированные компоненты при сборке.
