# `larena/layout`

> **Для кого:** разработчик композиции. **Результат:** описать структуру страницы
> без получения данных и решения прав. **Источник:** код пакета (`src/`),
> package README, CHANGELOG, Specs и Root tests. **Статус:** descriptor and
> render-plan foundation; список записей хранилища и выбор хранилища снимков
> проверены по коду `60cb676b` 26.10.2026.

Layout нормализует декларативную структуру областей, секций и блоков и строит
render plan. Текущие точки входа:
`PageAssemblyDescriptorNormalizer` и `MinimalCmsRenderPlanRuntime`.

- Composer: `larena/layout`.
- Владелец: page composition descriptor and render plan.
- Зрелость: bounded foundation.

Пакет зависит от Core. Он переносит структуру, props и ссылки; получение данных,
проверка прав и регистрация компонента принадлежат другим пакетам.

## Проверка

Root tests проверяют конструктор descriptor, версию и rollback принятой
композиции collection-screen.

## Ограничение

Текущий collection-screen уже универсального замысла Layout. Не расширяйте его
до произвольной страницы только на основании формата descriptor.

## Единая композиция

Layout реализует `LayoutArtifact`, неизменяемые ревизии, повторно используемые
placements, каталог, draft/publish/restore и активные compiled snapshots.
Системные артефакты читаются из пакетов, пользовательские — из БД. Канонический
JSON остаётся источником истины, а индекс родителей, потомков, слотов и порядка
перестраивается транзакционно как проекция. Старые `PageDescriptor` продолжают
читаться через совместимый адаптер без массовой миграции.

## История собранных результатов

Эта возможность принята в Layout `main` на ревизии
`157f60b9be1bc350f91998fddd643288f0089936`. Рабочий сайт при этом не
переключался. Точные границы проверки указаны в
[плане интерфейсов](/standards/declarative-interface-program/).

Дополнительный контракт `CompiledPageSnapshotCatalog` предоставляет
авторизованное чтение истории снимков. Он реализован хранилищами БД и файлов,
проверяет целостность сохранённых результатов и поддерживает постраничное
чтение по идентификатору снимка. Список не является отдельным источником истины.
Контракт активации и отката `CompiledPageSnapshotStore` остаётся прежним.

Редактор обращается к этому контракту, а не читает таблицы Layout напрямую.
Отказ чтения повреждённой истории не переключает активный результат.
Подробности пользовательского поведения — в [публикации и откате](/operations/composition-publication/).

Если изменение Setting влияет на несколько активных страниц, приложение
передаёт Layout ожидаемые ревизии всех снимков и активирует новый набор в общей
транзакции Setting. Layout по-прежнему владеет каждым снимком отдельно; digest
набора служит проверкой согласованности, а не новым хранилищем страниц.

Принятая ревизия Layout также предоставляет проверяемые режимы областей `inherit`,
`replace` и `empty`. Приложение регистрирует соответствие слотов областям и
значения по умолчанию отдельно для сайта, раздела и страницы. Reset удаляет
локальное переопределение. Пустая обязательная область или неизвестное имя
отклоняются до сохранения ревизии; активный снимок остаётся прежним.

## Где хранятся снимки

Провайдер Layout сам связывает хранилище описаний страниц и хранилище собранных
снимков. Какое хранилище снимков использовать, задаёт настройка
`larena-layout.snapshots.store`: `file` (по умолчанию) или `database`. Файловое
хранилище держит снимки в папке `larena-layout.snapshots.root`; если папку
нельзя создать, Layout отказывает с `layout_snapshot_root_invalid`. Приложение
обязано предоставить политику прав на страницы
(`PageDescriptorAuthorizationPolicy`), иначе хранилища не создаются.

## Список записей хранилища на странице

Блок `larena.list` с привязкой `storage_list` показывает на странице
опубликованные записи хранилища. Привязка выглядит так:
`{target, selector: "$", query: {filters, sort, limit, search}}`.

- Layout проверяет форму запроса, а поля запроса при сохранении страницы
  проверяет приложение через `PageBindingValidator`.
- Список не попадает в собранный снимок. Поэтому публикация записи не делает
  опубликованную страницу устаревшей: приложение читает список на каждом запросе
  через `PageProjectionResolver::resolveRequestBinding`.
- Какие хранилища и поля можно выбрать для списка, приложение сообщает через
  `StorageListTargets`: где лежат описания страниц сайта и какие публичные поля
  можно сортировать, фильтровать и искать.
- `StorageListPageBlocks` — общий помощник, который ставит блок списка на
  страницу `site.{key}`, читает его и убирает. Остальное содержимое страницы
  сохраняется; страница без описания получает его.

Layout не знает конкретных хранилищ: данные и права остаются у приложения и
Storage.

## Имена без версий

Снимки страниц, их активные указатели, каталоги пакетов, артефакты, сборки
страниц и рецепты названы без номера версии и несут версию полем
`schema_version`. Данные старой формы по-прежнему читаются, а сохранённый
документ сохраняет свою форму, чтобы его хеш совпадал.

## Именованные области и scope

Артефакт с компонентом `layout.regions` объявляет свои области (имя, роль
ориентира, расположение, подпись); каждая область — отдельный слот артефакта,
поэтому наследование по областям работает на прежней модели слотов. Layout
переносит области в Recipe как узлы `layout.region`. Детям `layout.scope`,
которые названы в маршрутах, Layout добавляет расширение endpoint с именем
размещения. Адаптер Recipe передаёт Framework реестр портов продукта. Принято в
Layout `main` на ревизии `5c098f51e497944f50ee8ae719d91077b949e0ed`.
