# Стандарты и контракты

> **Для кого:** разработчик и сопровождающий. **Результат:** найти владельца и
> обязательную границу до изменения кода. **Источники:** `larena-specs/docs/standards`.
> **Статус:** проверенная редакционная проекция; Specs остаётся каноническим источником.

## Пакетная граница

Каждая возможность принадлежит одному пакету. Соседний пакет использует её
через публичный контракт, а не через внутреннее хранилище. Composer-зависимость
должна совпадать с реальным направлением вызова.

Пример: `auth` устанавливает личность, `access` решает право, `admin` собирает
экран. Admin не должен самостоятельно определять парольную политику или
семантику роли.

## Публичный контракт

Публичным считается интерфейс, команда, конфигурация, маршрут, DTO или формат,
который явно предназначен для потребителя. Наличие PHP-класса в `src/` само по
себе не обещает совместимость. Справочник этого сайта перечисляет только
подтверждённые точки входа и направляет к package-owned документации.

## Данные и права

Мутация начинается с зарегистрированной операции и проверки Access. Storage
владеет записью и её версией; Property — типом и валидацией; Audit — отдельным
доказательством действия. Неизвестный контекст или операция должны приводить к
безопасному отказу.

## Композиция интерфейса

Layout переносит декларативную структуру и ссылки. UI разрешает только
зарегистрированные компоненты. Admin оркестрирует защищённую поверхность.
Blade содержит представление; подготовка данных и вычисления остаются в
контроллерах, моделях представления и сервисах.

## Локализация

Пользовательские строки должны идти через языковые ресурсы. Текущий пакет Lang
ещё не считается завершённой платформой локализации, поэтому новые обещания
fallback или форматирования требуют отдельного подтверждения.

## Документация и актуальность

Требование и архитектурное решение живут в Specs. Точный контракт обслуживания
живёт рядом с пакетом. Этот сайт объясняет общий путь на русском. При изменении
поведения команда `composer docs:status` сопоставляет изменённые публичные
контракты с конкретными страницами. Приёмка требует решения
`documentation_updated` либо `documentation_not_affected` с основанием.
Решение сохраняет ревизии, затронутые пути и доказательства обновлённых страниц.
Затем Docara отдельно проверяет связь 12 пакетных сущностей со справочными
маршрутами. Текст из Specs и README автоматически не переносится: автор
редактирует только связанные страницы и проверяет смысл.

Общий Root gate `composer docs:delta:check` объединяет этот контроль с уже
существующей проверкой внутренних developer docs. Подробная последовательность
команд находится на странице «Сборка и диагностика документации».

Основные канонические документы: Larena DNA, package DNA, package repository
structure, code quality and architecture, implementation quality и developer
documentation traceability standards в `larena-specs`.

## Декларативная композиция

Единый JSON-путь страницы, секции и блока закреплён в
[профиле декларативной композиции](/standards/declarative-composition/). Он
связывает Framework Composition Recipe с владельцами данных, версиями,
публикацией, кешем и откатом Larena.

## План развития интерфейсов

[Единая система интерфейсов](/standards/declarative-interface-program/) объясняет согласованную архитектуру, её текущие ограничения и последовательность внедрения. Это план развития, а не дополнительная отметка готовности CMS.
